# 胖客户端 / 瘦客户端设计 与 大群消息写入优化

日期: 2026-08-11
状态: 设计讨论纪要（不含实现）
适用工程: im-service（logic / fanout / gateway / Postgres / Redis / Kafka）

---

## 第一部分：胖客户端 vs 瘦客户端

### 1.1 两种模型的本质区别

| | 瘦客户端（thin） | 胖客户端（fat） |
|---|---|---|
| 数据的家 | 服务端 | **客户端本地库**（SQLite / IndexedDB） |
| 日常读取 | 每次向服务端拉 | **读本地，不发网络请求** |
| 服务端角色 | 数据库 + 显示后端 | **事件投递管道 + 离线暂存箱** |
| 典型代表 | 简单 Web IM | 微信 / QQ / 钉钉 |
| 离线可用 | 不可用 | 可翻历史、切会话零延迟 |

一句话：**瘦客户端"服务端是数据库、客户端是显示器"；胖客户端"客户端本地才是数据的家，服务端只负责可靠地把事件送达 + 离线暂存"。**

im-service 现状偏瘦客户端：前端每次向服务端拉会话列表和消息（`frontend/`），`Sync` 用时间戳做增量。

### 1.2 胖客户端的三个动作

胖客户端把 IM 简化成三件事，**在线推的和离线补的是同一个事件流**（一个实时、一个批量）：

1. **在线：实时推。** 长连接（WebSocket gateway）把新消息推给在线设备，客户端写入本地库并刷新 UI。
2. **离线：服务端暂存。** 推不到时，服务端把"本该送给你的事件"存进**收件箱**（按 uid 归属、带顺序的事件队列）。
3. **上线：增量补齐。** 客户端报"我上次同步到第 X 号"，服务端返回 X 之后的全部事件，客户端逐条写入本地库。

### 1.3 灵魂：单调递增的同步序列（sync key）

上线补齐里的 "X" 是整套设计的心脏，要求：

- **单调递增，per-user**（每个用户一条自己的序列；微信叫 sync key）。
- 客户端只需记住一个数，上线报它即可，无需逐会话询问。

**为什么不能用时间戳**（这是 im-service 现在 `Sync(last_sync_at)` 要改的点）：
- 同一毫秒多条消息会撞，`> last_sync_at` 漏或重。
- 机器时钟漂移/回拨不可靠。
- 递增序号天然无歧义：`> X` 就是"没见过的"，不多不少。

未读数同理：会话内也有 seq，未读 = 会话最新 seq − 已读 seq，一次减法，不用 `COUNT(*)`。

### 1.4 可靠投递：不丢、不重

分布式铁律：**服务端无法单方面确认"客户端收到了"**（TCP 成功只代表进了本机缓冲区；连接可能半死；客户端可能收到未落库就崩）。送达是"两个人的事"，必须有客户端反馈。所以：

1. **定序发号**：服务端为每个事件在收件箱里分配连续 seq。
2. **反馈 = ACK 或上线报位点**："我到 X 了"本身就是一种 ACK（X 及以前都确认收到）。没等到反馈就认为没送达，重发。收件箱条目在确认前不删。
3. **幂等去重**：因"至少一次投递"，同一条可能收到两遍，客户端靠 msg_id / 会话内 seq 去重。

**至少一次投递 + 客户端幂等 = 最终恰好一次。**

关于"是否需要客户端逐条校验 seq 连续性"（讨论结论）：
- 若**一切走收件箱 + 报位点补齐**（不抄"在线直推跳收件箱"的近道）→ **不需要**逐条校验，靠"报位点拉增量 + 请求整体重试"即可。
- 逐条连续性校验只是给"在线直推、不写收件箱"那条快路做丢包探测。**多设备场景下收件箱必写**（见下），因此走前者，连续性校验非必需；但**幂等去重永远需要**（实时推 + 收件箱补齐会让同一条到两次）。

### 1.5 发送端细节

- **乐观上屏**：客户端先生成本地临时 id，消息立刻显示（"发送中"），服务端落库分配真实 id/seq 后替换。这是"零延迟发送"的原理。
- **去重键（client_msg_id）**：网络抖动重发时，服务端靠客户端生成的唯一键去重，避免入库两条。

### 1.6 多设备

- 每个设备各有本地库、各有自己的 sync key（手机到 X、电脑到 Y，互相独立）。
- 收件箱是**账号级**的，每个设备各按自己的 sync key 补齐。
- "我发了""我读了"也作为事件同步给自己其它设备（手机读了电脑红点消）。
- **关键推论**："在线"是针对某个设备的，不是针对人。手机在线不代表电脑在线，所以**消息必须持久化，不能因为某设备在线就跳过**。

## 第二部分：胖客户端下的大群写入优化（推拉分型）

### 2.1 核心矛盾

胖客户端多设备铁律要求"收件箱必写、一条不跳"。收件箱是 **per-user** 的 → 万人群一条消息 = 写一万行收件箱，写放大原封不动地回来（只是从 `user_conversations` 换成收件箱表）。

**破解**："收件箱必写"是**写扩散（push）模式**下的铁律。大群的解法是**根本不进收件箱**，改用**读扩散（pull）**——消息存一份，成员按游标来拉。

### 2.2 按成员数阈值分型（每个会话打一个 `fanout_mode` 标签）

| | 小群 / DM（`push`，< 阈值） | 大群（`pull`，≥ 阈值） |
|---|---|---|
| `messages` 正文 | 存一份 | 存一份 |
| **收件箱（per-user）** | **每人写一行** | **不写** |
| 一条消息写放大 | O(成员数)，≤ 阈值可接受 | **O(1)** |
| 可靠性靠 | 收件箱 + ACK/重拉 | 消息存一份 + 按会话 pull |
| 多设备靠 | 各设备读自己的收件箱 | 各设备按自己游标独立 pull |
| 同步进度（游标） | 收件箱位点（per-user inbox seq） | 会话成员行游标（会话 `last_msg_seq` / 我的 `last_read_seq`） |
| 在线推送 | 逐个 Push（人少） | MultiPush 按网关聚合 + chunk |

**阈值建议 500**（微信群上限即 500，正是"写扩散还划算"的经验临界点，可配置、压测调整）。

**pull 天生解决"不丢 + 多设备"，零 per-user 写**：消息在 `messages` 存一份，任何设备按 `seq > 自己游标` 拉，拉不全就重拉，不依赖"当时推没推到"；设备之间互不影响，无需为任一设备写任何东西。

### 2.3 打标签（fanout_mode）的逻辑

**标签存哪**：`conversations.fanout_mode`（`push` | `pull`），默认 `push`。它是发消息时决定"写收件箱扩散"还是"只存一份走 pull"的唯一开关。配套字段 `conversations.member_count`（成员数，增删成员时维护）。

**谁来判定 / 何时判定**：由**成员数**派生，但**不在发消息热路径里判断**（发消息只读 `fanout_mode` 这个已算好的标签，不实时数成员）。判定发生在**成员变更时**（建群、加人、批量导入）：

```
成员变更后：
  member_count = 新成员数
  if fanout_mode == 'push' && member_count >= THRESHOLD:
      fanout_mode = 'pull'        // 触发升级（见下方迁移）
  // 无 pull → push 的反向判断
```

- **阈值 THRESHOLD**：建议 500（微信群上限即 500，写扩散经验临界点），放配置，压测后调整。
- **判定要幂等 + 串行**：并发加人可能同时触发升级，用会话级锁（可复用 `pkg/redisstore/lock.go`）串行化，避免重复迁移。
- **边界抖动**：成员数在阈值附近反复加/删人时，因为**单向不回切**（见下），不会来回抖动——一旦升级就固定，天然稳定。

**建群即大群的情况**：若建群时（`CreateGroup`）初始成员就 ≥ 阈值（如企业批量拉群、导入通讯录建群），直接以 `pull` 建立，不走"先 push 再升级"。所以判定逻辑在**建群**和**加人**两个入口都要有。

### 2.4 能否转化：单向升级，不可回切（sticky）

**方向不对称，这是整个状态机的核心结论：**

- **小 → 大（push → pull）：可以，且免费。**
  - 切换前一直在写收件箱，切换点之前的消息成员都已收到/能从收件箱补齐，**无空洞**。
  - 切换动作本身只是"把标签置 pull，以后发消息不再写收件箱"。
  - **需要做的一次性对齐**：把每个成员 `user_conversations` 行的已读位点/游标对齐到当前会话 `last_msg_seq`，使其后续作为"只读游标行"参与 pull 补齐（见 §2.9）。已有的行天然变成游标行，无需回填历史。

- **大 → 小（pull → push）：不做（禁止回切）。**
  - **根本原因**：pull 期间消息**只写进 `messages` 一份，从没进过任何成员的收件箱**。若切回 push，上线补齐走收件箱轨，**扫不到 pull 时期产生的消息**——增量同步 / 未读 / 会话列表冒泡这一层会漏掉那段。
  - **注意区分**：断的只是"增量同步 / 主动补齐 / 列表冒泡"这层；**用户主动点开会话、按会话 id 直接查 `messages` 的历史读取（`GetMessages`）在任何 mode 下都拿得到**，消息本身不丢。
  - **若一定要回切**（大群缩员后想恢复写扩散体验，罕见运维操作）：必须先做**收件箱回填**——把切换点的状态灌进每个当前成员的收件箱/游标，让收件箱轨能接续 pull 期的进度。属低频、重操作，加锁串行、可离线批处理。**默认不实现。**

**结论**：判定规则只有单向一条 —— `member_count 越过阈值 → 置 pull`，**无反向规则**。一个群一旦成为大群就永久保持 pull，省掉回填收件箱的麻烦，也避免边界抖动。

### 2.5 迁移动作（push → pull）清单

升级发生时（在会话锁内）：

1. 置 `conversations.fanout_mode = 'pull'`。
2. 确保会话行的 `last_msg_seq` / `last_msg_*` 已就绪（作为 pull 的公共信息源）。
3. 对齐每个成员 `user_conversations` 的游标：`last_read_seq` 保持现值（已读进度不变），该行此后不再随发消息更新，退化为只读游标行。
4. 刷新 Redis 成员缓存 / 会话 seq 计数器（`conv:{id}:seq` 初始化为当前 `last_msg_seq`）。
5. 之后新消息走 §2.6 的 O(1) 写路径。

迁移期间到达的消息：因为切换点前后收件箱都不产生空洞（切换前有收件箱、切换后有 `messages` + 游标），双轨归并（§2.10）能无缝接上。

### 2.6 大群写路径（O(1)）

1. 派会话内 `seq`（万人群高频，用 Redis `INCR conv:{id}:seq` 发号最合适）。
2. 写 1 行 `messages`。
3. 更新会话行 `last_msg_seq / last_msg_*`（**热行问题**：万人同发都 UPDATE 这一行会行锁争抢 → `last_seq` 只在 Redis 维护，DB 行懒更新/定期刷，会话列表"最后一条"允许弱一致）。
4. **不写任何成员收件箱。**

DB 写从 N+1 降到 O(1)，与群大小无关。

### 2.7 大群在线推送（尽力而为，不背可靠性）

**第一原则**：大群推送漏了不用管，可靠性交给 pull 兜底。目标只有"让在线的人尽快看到，且成本不随群大小爆炸"。

现状瓶颈（`fanout/fanout.go`）：逐成员 `GetRoute`（N 次 Redis）+ 逐成员 gRPC `Push`（N 次 RPC），卡在 `sem=50`。三刀砍放大：

**第一刀——批量查路由**：一次 `MGET`（或 pipeline）捞回这批人的网关，取代逐个 `GetRoute`（`fanout.go:80`）。更进一步：维护"群在线成员集"或与全局在线集求交，离线的不进推送流程。

**第二刀——按网关聚合（核心）**：在线成员按所在网关分桶，每台网关**只发 1 次 `MultiPush`**（带 uid 列表 + 消息体），网关在本地 Hub 循环 uid 逐个 `WriteMessage`。RPC 从 O(在线人数) 降到 **O(网关数)**，消息体网络传输也只 O(网关数)。

```proto
message MultiPushRequest { repeated int64 user_ids = 1; bytes payload = 2; }
rpc MultiPush(MultiPushRequest) returns (MultiPushResponse);
```

**第三刀——单网关人多要拆**（如某网关分到 1000 人）：
- **网关内（主要矛盾）**：不要单 goroutine 顺序推 1000 个 → 用 **worker pool 并行** + 每个 `WriteMessage` 带**写超时**，**慢连接超时即弃**（靠 pull 兜底），防队头阻塞（一个慢连接拖住其余 999）。每连接自带锁（`Conn.mu`），并行写不同连接安全。
- **分发侧**：对单网关 uid 列表按固定 **chunk（如 200）切分**，控制 gRPC 包体积（避免撞 4MB 上限）、支持流水线、细粒度重试。500 人群通常到不了，可暂不 chunk。

**扇出本身的扩展**：一期进程内 worker pool；二期 Kafka 分片（logic 侧按成员哈希拆子任务到不同 partition，多个 fanout 实例并行消费）。

**万人群三个洪流问题**：
1. **高频发言洪流** → 合并推送（几百 ms 窗口内多条攒成一个批次下发）。
2. **惊群拉取**（热消息推下去几千客户端同时拉打 DB）→ 群最近消息缓存 Redis（`conv:{id}:recent`）；推送直接带消息体，收到就不用再拉。
3. **非活跃成员不值得推** → 只推活跃/最近打开过的在线成员，其余纯靠上线 pull。

### 2.8 小群写路径（push / 写扩散）

500 人内绝大多数会话走这条，**必须持久化**：

1. 写 1 行 `messages`（事实源）。
2. **给每个成员写一条收件箱**（per-user，带连续 inbox seq，只存指针 msg_id + seq + 送达状态，不存正文）。
3. 在线成员实时推（人少，逐个 Push 即可）。
4. 离线/漏推靠收件箱：上线报位点拉 `> X`。
5. 客户端按 msg_id 幂等去重。

收件箱 seq 是 **per-user 逐 1 连续**、原子发号（收件箱行与取号同事务，别留空洞）。

### 2.9 写信箱 与 push 的顺序（讨论结论）

- **无强顺序依赖**：push 用的是消息本身（`messages` 落库那刻即备齐），不依赖收件箱写完。
- **业界主流仍是"先持久化、后推送"**——不是因为依赖，而是让失败倒向"延迟"而非"永久丢失"：先 push 后写信箱且信箱失败 → 在线看到了但换设备永久丢；先持久化后 push → 最坏只是晚点看到。
- **两段式**（im-service 天然是这个形状：logic 写 messages + 发 Kafka → fanout 消费）：
  - **第一段（同步，必成功）**：写 `messages`（一份，快）。到这消息已"永不丢失"，`SendMessage` 可返回成功。
  - **第二段（异步，并行，最终一致）**：push（尽力而为，丢了没事）∥ 写收件箱（失败重试、幂等）。二者无顺序。
- **关键前提**：收件箱写入必须**保证最终成功**，否则"messages 不丢 + 并行"仍会出现"看到 push 但换设备丢消息"。靠 Kafka：**handler 失败不 commit offset → 重投 → 幂等去重**。
  - ⚠️ **现存 bug**：`pkg/kafka/consumer.go:56-59` handler 失败只打日志、仍无条件 `MarkMessage`（commit）。扇出失败会永久丢，需改为"失败不 commit，让 Kafka 重投"。
- 若连"重试期间换设备"的几秒窗口都不接受 → 退回**同步写信箱成功才 push**（延迟高、吞吐低，强一致）。

### 2.10 上线补齐：双轨归并

用户上线报收件箱位点，服务端并起两轨：

1. **收件箱轨（push 会话）**：拉收件箱 `> X` 的所有事件（小群/DM 新消息、好友事件等）。
2. **大群轨（pull 会话）**：服务端一次 SQL 扫我的大群成员行 —— `我的成员行 JOIN 会话行 WHERE 会话.last_msg_seq > 我.last_read_seq` —— 得出"哪些大群有我没看的新消息"清单。**不在收件箱里，是读出来的**（发消息时零成本）。客户端一个大群游标都不用替它操心，服务端算好告诉它；客户端只在真去拉某群时用返回的游标做 `> seq` 拉取。
3. **归并**：在**会话列表层**把两轨合并、按最后消息时间排序、各自算未读（收件箱轨按位点差、大群轨按 `last_msg_seq - last_read_seq`，展示封顶 `99+`）、分页。前端不感知背后两轨。
4. **去重**：迁移过的会话（小→大）可能收件箱有旧条目、pull 轨又报新消息 → 按会话 id 合并成一项，消息层按 msg_id 去重。

### 2.11 游标的"家"（澄清）

游标不只属于收件箱：

| 进度类型 | 存在哪 | 含义 |
|---|---|---|
| 收件箱位点（小群/DM） | 收件箱 / per-user sync key | "我收件箱到 X" |
| 大群"最新到哪" | `conversations.last_msg_seq`（会话一行，公共） | "这个群最新 seq 900" |
| 大群"我读到哪" | `user_conversations.last_read_seq`（我在该群的成员行，私有） | "我读到 seq 850" |

大群成员行**发消息时不更新**（不写放大），只在 `MarkRead` 更新 `last_read_seq`、入群时 seed。

## 第三部分：分库分表下的写入（以 uid 分片 + db proxy）

### 3.1 分片键设计

| 表 | 分片键 | 理由 |
|---|---|---|
| 收件箱 inbox | **uid** | 高频是"读我的收件箱"，必须单分片 |
| `user_conversations` | **uid** | "读我的会话列表"单分片 |
| `messages` | **会话 id / 消息 id** | "读某会话历史"聚在一起，单分片翻页 |
| 会话成员关系 | 可能**双写**（按 uid 一份、按 conv 一份） | "我在哪些群"按 uid，"这群有哪些人"按 conv |

**per-user seq 在分片下天然简单**：seq 是 per-user 的，用户数据就在自己那片 → 取号就是该用户所在**单分片内的行锁自增**（`UPDATE ... RETURNING`），不跨分片、无需全局发号器。这是选 uid 分片的又一好处。

### 3.2 写扩散跨分片：靠幂等 + 重试，不用分布式事务

- 收件箱按 uid 分片 → 群成员的收件箱条目**天然分散到各分片**，这正是目标（读收件箱单分片）。**不需要、也不应塞进一个分片。**
- 一次写 N 条跨分片 = N 个独立单分片写，**不追求原子**。靠 `(uid, msg_id)` 唯一键 + 重试保证最终都成功。**不要用 2PC/TCC**（慢、复杂，收件箱扇出不需要这种强度）。
- 最稳形态是**异步扇出**：同步只写 `messages` + 发 Kafka（现有），消费者把收件箱写到各分片，Kafka 至少一次 + 幂等消化跨分片可靠性。

### 3.3 批量 INSERT 与 proxy（分片对业务透明）

- **fanout 的分批只按"固定批大小"分（如每 200），绝不按分片分**——分片是 proxy 内部实现，对 fanout 透明；泄漏到业务层是耦合反模式（分片规则一变业务全改）。你的直觉正确。
- 可以写**一条** `INSERT ... VALUES(多行) ON CONFLICT DO NOTHING`：主流 proxy 会解析每行分片键、**按分片分组重写成 N 条子 SQL 分发**——书写一条，执行 N 条。
- 但它**不是原子的**：部分分片可能失败、已成功的不回滚 → 必须配 `ON CONFLICT DO NOTHING` + 重试。
- **seq 不能靠跨分片批量 INSERT 的 `RETURNING` 拿回** → 提前在应用层/Redis 派好带进 VALUES。
- 具体能否一条搞定、行数上限，**取决于所用 proxy（ShardingSphere/MyCat/Vitess/自研），需查其文档**。

### 3.4 收件箱内部是否并行 insert

- **能批量就批量（免并行）**：500 人几条批量 INSERT 搞定，顺序发即可；proxy 内部会自己并发分发到各分片，瓶颈那段已并发。
- 只有**被迫逐条写**（proxy 不支持跨分片批量）才用 worker pool 并行补救。
- 别一上来就并行单条——那是把批量能解决的问题复杂化。

## 第四部分：落到 im-service 的差距与分期

### 4.1 现状 vs 目标

| 能力 | 现状 | 要补 |
|---|---|---|
| 实时推 | ✅ gateway WS + fanout | 有 |
| 离线暂存 | ❌ 离线丢（`fanout.go:80` 查不到路由即 return） | **收件箱表持久化未送达事件** |
| 增量补齐 | ⚠️ `Sync(last_sync_at)` 用时间戳 | **换单调 seq / sync key** |
| 可靠投递 | ❌ 无 ACK/重发；`consumer.go:58` 失败仍 commit | **失败不 commit + 幂等去重** |
| 会话内 seq | ❌ 用全局 msg id | 引入（未读=差值） |
| 推拉分型 | ❌ 全 push | `conversations.fanout_mode` + 阈值 |
| 大群推送 | ❌ 逐成员 Push | 批量路由 + `MultiPush` + chunk |
| 本地库 | ❌ Web 前端每次拉 | （纯胖客户端才需）IndexedDB |

### 4.2 分期建议

- **一期**：会话内 seq + `fanout_mode` + 大群 O(1) 写路径 + Sync 双轨归并 + 未读改差值。解决 DB 写放大这个致命瓶颈。
- **二期**：批量路由（MGET）+ `MultiPush` 按网关聚合 + chunk + 慢连接隔离。解决推送放大。
- **三期**：Kafka 分片 fanout + 在线成员集 + 合并推送 + 最近消息缓存。解决单实例扩散上限与万人群洪流。
- **可靠性专项**（可与一期并行，其实更基础）：收件箱表 + 修 `consumer.go` 失败重投 + 幂等键，让系统"不丢消息"。

### 4.3 待确认

- 阈值取值（默认 500）需压测。
- `seq` 派号：Redis `INCR`（快，需保证与落库一致）vs Postgres 事务内取（强一致，略慢）。大群倾向 Redis。
- 是否要做纯胖客户端（前端本地库），还是服务端优化为主、前端仍按需拉。
- 大群是否需要"免打扰/不计未读"等产品策略。
